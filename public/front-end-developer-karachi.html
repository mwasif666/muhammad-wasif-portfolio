What senior actually means here

Anyone can put a design on screen once. The difference shows up six months later, when someone has to change it. What I am paid for:

  • Components with one job. A card renders a card. It does not also fetch, sort and decide what a card is.
  • Layouts that hold under real content. Designs are tested with the long product name and the three-line heading, not the tidy placeholder.
  • Loading, empty and error states built with the happy path — the three screens most projects discover only after a client does.
  • State kept where it is used. Global stores are for genuinely global things, not for whatever was inconvenient to pass down.
  • Semantic HTML. Real buttons, real headings, real labels. The same work that makes a page accessible is what makes it legible to search engines.

The stack I work in daily

React is where the most hours are. Next.js when pages need to be server-rendered so they load fast and can actually be crawled. TypeScript where the data is complex enough to earn the build step — and plain JavaScript where it is not, because a five-page marketing site does not need a type system.

Styling in Tailwind, CSS Modules, Sass or hand-written CSS, depending on what the team maintaining it will be comfortable with. Bootstrap when a project wants a dependable grid and nothing exotic. GSAP and scroll-driven motion when the design calls for it — this portfolio is that, and it still holds its Core Web Vitals.

Speed and accessibility are the work, not extras

Most of your visitors arrive on a phone, on a connection that is not yours, holding it one-handed. So the same checklist runs on every build: image formats and sizing, font loading strategy, what is genuinely in the JavaScript bundle, layout shift from anything that arrives late, and how long the main thread is busy before the page responds to a tap.

Accessibility gets the same treatment: focus that goes where you expect, contrast that survives sunlight, controls reachable by keyboard, and headings that describe the page instead of just being large. It is not a compliance chore — it is the same discipline that makes an interface feel solid.

Frequently asked questions

What does a front-end developer do?

Builds everything the visitor sees and interacts with — layout, typography, navigation, forms, animation, responsive behaviour — and makes it work across browsers, screen sizes and input methods. On a modern project that also means component architecture, performance budgets and accessibility, not just turning a design into HTML.

Can you build from a Figma design?

Yes. Figma, XD, a PDF, or a live site you want rebuilt. I will also flag anything in the design that will not survive real content or a 360px screen before building it, which is cheaper than finding out afterwards.

Do you use React for every project?

No, and that matters. React and Next.js earn their complexity on component-heavy or content-driven products. A brochure site is often better as clean HTML, CSS and JavaScript — it loads faster and costs less to build and host. Picking the lightest tool that does the job is part of the work.

Can you make my existing site faster?

Usually, and often significantly. An audit covers bundle size, image handling, font loading, layout shift and third-party scripts, and comes back with specific fixes ranked by what will actually move — not a Lighthouse screenshot with no plan attached.

Do you handle the backend too?

I ship it, and I am honest about the level. Laravel with MySQL and Node with MongoDB are both in production on delivered projects. Front end is where the seniority is; for a demanding backend I will say so upfront and we bring in a specialist rather than me learning on your budget.
